# SPEC 歧义与待澄清清单

> 来源：独立第二实现过程（实现者只读 SPEC.md 与适配器契约，未接触任何现有实现）。
> 每条都是「两个理性实现者可能做出不同选择」的地方——澄清一条，互通性多一分。
> 处置建议供 SPEC 维护者参考；本文档本身先如实记录。

1. **宽松解析的观察出口**：语义 3 要求缺段空串/缺字段默认值/未知字段保留，但最小适配器契约的 `load` 只返回全文——这些行为对外不可观察。建议：SPEC 定义一个可选的「解析面」（如 `parseCard(text) → {frontmatter, sections}`），符合性套件才有抓手。
2. **`writeCard(text)` 的 text 语义**：全文覆写？正文注入？忽略？未定义。建议：明确「带 frontmatter 时实现可只校验不改写；id 行必须与生成文件名一致」。
3. **`writeRaw` 非 .md 文件名**：契约允许任意文件名，但 id 定义 = 文件名去 `.md`、取件按 `<id>.md` 寻址。建议：明确非 .md 文件在 pending 的可见性（忽略 or 补后缀）。
4. **load 侧 id 闸精度**：生成侧形态严格有明文；取件侧对宽松卡（任意文件名 id）用白名单会挡死合法卡。建议：SPEC 区分「生成侧白名单」与「取件侧黑名单 + 包含性校验」。
5. **archived「最近 50 份」排序口径**：mtime 还是 id 时间戳？同毫秒批量写入时两种口径结果不同。建议：明示 mtime 优先、id 时间戳 tiebreak。
6. **二次取件报错的匹配方式**：参考文案「收件箱无此待取件」是全等要求还是建议文案？错误类型是否须特定？建议：标记为「文案建议、抛错必须」。
7. **必填字段的消费侧行为**：字段表 `from.agent/from.session` 必填（默认「—」），语义 3 又说缺字段给默认值——消费侧遇缺失必填字段到底报错还是默认空串？建议：消费侧一律默认空串（宽松模式优先），必填只约束生产者。
8. **`handoff` 字段的非法取值**：更高版本容错有明文；字符串 `"1"`、`0`、乱值未说。建议：parseInt 可解析即按其值，不可解析按 1。
9. **`tasks` 元素清洗**：缺 `text`/`status` 越界的任务项原样保留还是剔除？建议：原样保留（未知数据纪律同 frontmatter）。
10. **「建议加载」段的生产义务**：语义 5「建议带」+ 模板标可选——已无歧义，但独立实现仍提出「严格数段=6 会误伤」，记录在案（套件 C4 只查六段必选，允许多段）。
